# Spec Delta

## Purpose

定义玩家进度、猫咪生活状态、设施、布局、库存和货币的保存与恢复行为，支持离线照护及护理中断恢复，并以云端已确认状态及依赖有序操作处理多设备冲突，避免重复交易和重复发放照护效果。

## ADDED Requirements

### Requirement: 玩家进度必须在游戏重启后恢复
系统 MUST 保存玩家进度、货币、猫咪、咪窝、库存及设置，以及情绪/关系/偏好/精力、食盆表现进度、猫砂余量及结团、拥有物实例、布局版本和护理会话。重启须恢复最近可用状态，区分已确认数据与待确认预测。

玩家档案 MUST 以服务端从微信云函数调用上下文取得的身份为准。客户端不得通过请求参数指定其他玩家 ID，也不得直接提交整份存档覆盖服务端状态。玩家最高解锁关卡等单玩家进度可与玩家主记录合并；逐关成绩仍按玩家和关卡分别保存。

#### Scenario: 玩家重新启动游戏
- **WHEN** 玩家在已有存档后重新打开游戏
- **THEN** 系统恢复其最近一次已确认的进度和状态

#### Scenario: 云端暂不可用
- **WHEN** 玩家启动时无法连接云端但存在有效本地存档
- **THEN** 系统允许玩家从本地存档继续进行支持的离线操作

### Requirement: 玩家档案必须使用可信微信身份隔离
系统 MUST 以云函数调用上下文中的微信身份定位玩家。客户端不得指定其他玩家 ID，也不得以整份客户端快照覆盖云端状态。

#### Scenario: 客户端尝试读取或修改其他玩家存档
- **WHEN** 客户端请求中包含其他玩家标识，或试图直接写入整份玩家快照
- **THEN** 服务端忽略不可信身份字段或拒绝该写操作，只允许访问云函数身份上下文对应玩家的数据

### Requirement: 写操作必须幂等并校验并发版本
服务端 MUST 按玩家和 `operationId` 去重写操作。同一 ID 的同一请求返回既有结果；不同请求复用该 ID 时拒绝。布局、猫咪等并发更新 MUST 校验预期版本。

#### Scenario: 请求 ID 被不同内容复用
- **WHEN** 服务端收到已处理 `operationId`，但请求内容与首次处理内容不同
- **THEN** 服务端返回 `OPERATION_ID_REUSED` 且不产生第二次状态变更

#### Scenario: 多设备提交过期状态
- **WHEN** 设备提交的猫咪或咪窝布局版本早于服务端当前版本
- **THEN** 服务端返回明确版本冲突及当前版本，不静默覆盖另一设备的更改

### Requirement: 后端存储必须保持身份和事务语义
系统 MUST 在实施前验证数据库与云函数的兼容性。关系型或文档型存储均须提供等价的身份隔离、事务、唯一性和版本校验语义。

#### Scenario: 部署方案不支持关系型参考模型
- **WHEN** 当前微信云开发环境不支持经验证的关系型数据库连接或关键事务能力
- **THEN** 实施前选用受支持的关系型服务或文档存储映射，并通过契约测试保持相同的数据一致性要求

### Requirement: 离线操作必须本地记录并等待云端校验
系统 MUST 在离线时记录可支持的玩家操作及其顺序；本地预测状态不得显示为云端已确认状态。

#### Scenario: 离线完成一局游戏
- **WHEN** 玩家离线完成一局并获得待同步奖励
- **THEN** 系统记录该操作及奖励请求，并将奖励标记为待确认

#### Scenario: 离线消费货币
- **WHEN** 玩家离线购买商品且本地预测余额足够
- **THEN** 系统记录购买请求为待确认，并在商品交付状态中标明其未获云端确认

### Requirement: 重连后云端必须校验并去重待同步操作
系统 MUST 将待同步操作提交给云端按顺序校验；每个操作 MUST 使用可去重标识，使重复提交不会重复发放奖励、扣款或交付商品。

#### Scenario: 待同步操作通过校验
- **WHEN** 云端收到有效且尚未处理的待同步操作
- **THEN** 云端确认该操作并更新权威玩家状态，客户端同步确认状态

#### Scenario: 重复提交已处理操作
- **WHEN** 云端收到具有已处理标识的重复操作
- **THEN** 云端返回先前处理结果且不再次执行其货币或库存变更

#### Scenario: 待同步操作未通过校验
- **WHEN** 云端判定待同步奖励、消费或状态变更不合法
- **THEN** 云端拒绝该操作，客户端丢弃对应预测变更并从最近的云端已确认状态恢复

#### Scenario: 部分操作冲突
- **WHEN** 玩家操作队列中部分请求通过校验而部分请求被拒绝
- **THEN** 系统保留已确认请求结果，并基于最新云端已确认状态处理后续请求，不以整份本地快照覆盖云端状态

### Requirement: 云端确认状态必须能安全写入本地
系统 MUST 在云端状态验证完成后更新本地已确认存档；同步中断时 MUST 保留可恢复的同步状态，避免把未确认快照标记为成功。

#### Scenario: 同步在确认前中断
- **WHEN** 客户端在收到云端确认前断线
- **THEN** 系统保留待确认操作以供后续重试，且不标记为已同步

#### Scenario: 同步成功
- **WHEN** 客户端收到云端已确认状态
- **THEN** 系统保存该状态为新的本地已确认基线并清除已处理操作

### Requirement: 生活操作必须有唯一标识和顺序依赖
系统 MUST 为喂食、有效玩耍结算、清洁区段、铲屎、补砂、整盆更换及布局保存记录操作标识、目标、版本和必要依赖，并按序校验。依赖未确认购买的操作须标明预测状态，前置被拒绝后不得保留其收益、库存或布局效果。

#### Scenario: 待确认购买被拒绝
- **WHEN** 玩家离线购买家具并预测摆放，云端随后拒绝该购买
- **THEN** 系统撤销依赖该实例的摆放，保留无关已确认结果，明确提示而不只扣款或保留幽灵家具

#### Scenario: 补砂前置库存冲突
- **WHEN** 补砂依赖的库存被云端判定不足
- **THEN** 系统拒绝该补砂及不再合法的依赖操作，从最新基线重算盆状态，不保留预测填入量

#### Scenario: 重复提交喂食
- **WHEN** 已成功结算的同一喂食操作因重启或重连再次提交
- **THEN** 系统返回既有结果，不重复扣食物、不重复增加饱食度、不以重试时间再次重置最后喂食时间

### Requirement: 生活设施补算必须有容量和时间边界
系统 MUST 保存各生活设施的最后补算游标，并以可信时间及配置补算未处理区间。重复进入、客户端时钟回拨和超长离线不得造成重复收益、负库存或无限结团，超容量区间须推进游标而不留待后续重放。

#### Scenario: 重复恢复同一离线时间段
- **WHEN** 客户端连续重启或重新同步同一已补算时间范围
- **THEN** 系统不重复扣砂、生成结团或恢复属性，已成功喂食动画不作为新的进食收益

### Requirement: 设施维护和布局冲突必须保持一致
系统 MUST 校验猫砂盆及布局版本、设施占用、物品所有权和实例唯一性。相冲突的并发操作不得部分写入；重连后按最新确认状态处理后续操作，并通知用户冲突及恢复结果。

#### Scenario: 两设备同时清理同一结团
- **WHEN** 两个请求针对同一结团或过时盆状态提交
- **THEN** 同一结团只清除一次，其他请求返回既有结果或明确冲突，不覆盖后来生成的结团

#### Scenario: 同一家具并发布置
- **WHEN** 两设备把同一家具实例摆放到不同咪窝
- **THEN** 系统最多确认一个位置，另一请求明确冲突，不复制实例

### Requirement: 护理中断必须恢复已完成阶段且不重复结算
系统 MUST 在切后台或退出时保存护理会话、猫咪湿润状态、已结算区段和冷却记录。恢复须继续有效阶段或提供协助擦干，不从头重发清洁效果，不同时恢复互斥活动。

#### Scenario: 吹干途中重新启动
- **WHEN** 猫在吹干阶段尚未完成时应用重启
- **THEN** 系统恢复同一护理会话并提供继续或协助完成，已结算清洁及冷却不重复计算

### Requirement: 存储错误和预览模式必须明确可见
系统 MUST 将微信正式存储与编辑器本地演示隔离，不把预览结果标为云同步成功。读取损坏或写入失败 MUST 显示错误和恢复选择，保留可用已确认基线，不静默清空存档或宣称成功。

#### Scenario: 本地存档无法读取
- **WHEN** 存档损坏或设备存储失败
- **THEN** 系统通知用户，提供重试或恢复已确认存档等可行选择，不自动重置财产或伪报已保存
