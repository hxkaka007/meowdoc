# Spec Delta

## Purpose

定义游戏货币、商店目录、购买和使用规则，区分猫砂等计量消耗品与家具玩具等耐用实例，保证闯关奖励、日常照护和空间布置共享一致、可追溯且不重复扣除的经济状态。

## ADDED Requirements

### Requirement: 玩家货币余额必须保持非负并可追溯
系统 MUST 维护玩家的喵币和钻石余额；每次奖励或消费 MUST 产生可确认的余额变化，并在 `player_currency_ledger` 记录币种、正负变更量、变更后余额、业务来源、幂等操作标识及服务端记账时间。任何操作不得使余额低于零。当前余额与流水是不同用途的记录，涉及货币的业务 MUST 在同一事务中更新 `wallets`、追加流水和保存操作回执。

#### Scenario: 玩家获得喵币奖励
- **WHEN** 玩家完成符合奖励条件的游戏行为
- **THEN** 系统按配置增加喵币余额并反馈到账数量

#### Scenario: 玩家尝试超出余额消费
- **WHEN** 玩家操作所需货币多于其可用余额
- **THEN** 系统拒绝该操作且保持余额不变

### Requirement: 商店商品必须通过配置目录展示
系统 MUST 展示已解锁商品的分类、价格、货币类型、效果、消耗类型和已拥有量，并仅允许购买可用商品。食物、猫砂、家具和玩具须可分类查看；可摆物须展示占地和适用空间，基础猫砂须能用喵币购买而非仅靠钻石或广告。

家具和装饰的商品效果 MUST 限于外观、休息位置或互动锚点，不得提供猫咪属性加成或属性衰减减免。家具使用产生的互动结算 MUST 沿用对应互动规则与收益上限，不因商品价格或拥有数量提高。

#### Scenario: 展示商品信息
- **WHEN** 玩家打开商店或切换商品分类
- **THEN** 系统展示该分类下已解锁商品的价格、购买货币和效果

#### Scenario: 查看可摆放商品
- **WHEN** 玩家查看家具或可摆玩具
- **THEN** 系统展示空间预览、占地、适用场景及耐用/消耗类型，纯装饰不虚标照护收益

#### Scenario: 查看家具商品效果
- **WHEN** 玩家查看家具或装饰的商品详情
- **THEN** 系统只展示其外观、休息位置或互动用途，不将其描述为照护数值加成或衰减减免

### Requirement: 购买必须同时扣款并交付商品
系统 MUST 将一次购买作为单一可确认操作处理：购买成功时扣除对应货币并交付商品或应用其效果；失败时不得只扣款或只交付。

#### Scenario: 成功购买商品
- **WHEN** 玩家购买已解锁商品且余额足够
- **THEN** 系统扣除对应货币并将商品加入库存或应用其配置效果

#### Scenario: 商品未解锁或已不可购买
- **WHEN** 玩家购买未达到解锁条件或当前不可购买的商品
- **THEN** 系统拒绝购买且不改变余额和库存

#### Scenario: 购买过程中交易未能确认
- **WHEN** 购买无法获得成功确认
- **THEN** 系统不得将未确认交易同时记为扣款和商品交付成功

### Requirement: 可重复闯关不得重复发放一次性通关奖励
系统 MUST 记录关卡的奖励领取状态，并按关卡配置区分首次通关奖励与可重复获得的奖励。

#### Scenario: 玩家首次通关
- **WHEN** 玩家首次完成某关卡
- **THEN** 系统发放该关卡配置的通关奖励并记录已领取状态

#### Scenario: 玩家重玩已通关关卡
- **WHEN** 玩家重玩已领取首次通关奖励的关卡
- **THEN** 系统不重复发放该一次性奖励，但可发放明确配置为可重复的奖励

### Requirement: 猫砂库存必须保留可拆分用量
系统 MUST 将猫砂包转换为明确配置的库存计量，补砂只扣实际填入量，并保留未使用余量。猫砂购买与补砂为不同操作；库存、盆内余量及货币不得为负，取消、容量不足或请求失败不得部分扣除。

#### Scenario: 买一包后仅使用部分
- **WHEN** 玩家购买含配置用量的猫砂包并只补入其中一部分
- **THEN** 系统购买时增加完整库存，补砂时仅扣实际量，剩余库存可继续使用

#### Scenario: 补砂重复请求
- **WHEN** 同一补砂请求重试
- **THEN** 系统最多扣一次库存并填入一次，不重复收取货币

### Requirement: 耐用玩具和家具必须以独立实例持有
系统 MUST 为购买交付的耐用玩具、家具或设施维护唯一实例及所在背包/空间位置；使用耐用品不得按次扣除。消耗型玩具须在有效使用时按配置扣一次，拒绝或有效使用前取消不得扣除。

玩家库存 MUST 可由统一逻辑库存记录表达堆叠物和独立实例：堆叠物按玩家与商品 SKU 唯一汇总数量；独立实例每件一条记录，数量为 1，并以库存记录 ID 作为实例身份。商品目录 MUST 声明商品持有类型，服务端 MUST 拒绝商品类型与库存记录类型不一致的数据。布置位置和方向可单独保存，但必须引用同一唯一实例；摆放和收回不得复制实例。

玩家背包 MUST 按“家具”“玩具”“日用品”“食物”四类展示物品：家具类包括家具与装饰，玩具类包括耐用及消耗型玩具，日用品类包括猫砂等护理消耗物，食物类包括主粮与零食。每类 MUST 根据商品持有模型展示可用数量或独立实例；可重复使用的猫砂铲、梳理工具等不得作为消耗品按量扣除。该背包分类不要求商店使用相同分类。

#### Scenario: 多次使用逗猫棒
- **WHEN** 玩家在多次会话中使用同一已拥有耐用逗猫棒
- **THEN** 实例仍由玩家持有，不减少数量，互动收益按会话限额独立校验

#### Scenario: 按类别查看背包物品
- **WHEN** 玩家打开背包并切换“家具”“玩具”“日用品”或“食物”
- **THEN** 系统仅展示所选类别的物品，并按其持有模型显示堆叠数量或独立实例及所在位置

#### Scenario: 消耗型玩具取消或成功使用
- **WHEN** 玩家选择消耗型玩具后取消、猫拒绝，或会话首次发生有效使用
- **THEN** 取消和拒绝不扣库存；首次有效使用扣配置数量，后续动作或重试不重复扣除

#### Scenario: 家具购买后暂不布置
- **WHEN** 家具购买成功而玩家选择放入背包
- **THEN** 系统保留未摆放实例，不把它当作房间内设施，也不再次购买才能摆放

#### Scenario: 背包统一查询堆叠物与耐用品
- **WHEN** 玩家查询背包中的一种堆叠物及多件同 SKU 耐用品
- **THEN** 系统从统一逻辑库存返回堆叠数量及每件耐用品独立实例，并保持每个实例的唯一 ID 和位置

#### Scenario: 购买操作重试
- **WHEN** 同一购买因网络超时以相同 `operationId` 重试
- **THEN** 系统返回原交易结果，钱包流水和商品交付均不重复

### Requirement: 生活物资失败必须有明确反馈且不能强制购买
系统 MUST 在食物、猫砂或余额不足时说明缺少条件并提供可选商店入口，不自动扣款或强制广告。基础梳理工具和猫砂铲重复使用不得额外收费，停手、清理或忽略邀请不得自动产生付费交易。

#### Scenario: 无猫砂时打开补砂
- **WHEN** 库存不足以执行所选补砂操作
- **THEN** 系统说明可用量与所需量并保留原状态，玩家可自行选择商店或关闭
